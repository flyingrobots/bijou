\section{Hill}\label{record-130-hill}

\texttt{c\allowbreak{}r\allowbreak{}e\allowbreak{}a\allowbreak{}t\allowbreak{}e\allowbreak{}T\allowbreak{}u\allowbreak{}i\allowbreak{}A\allowbreak{}p\allowbreak{}p\allowbreak{}S\allowbreak{}k\allowbreak{}e\allowbreak{}l\allowbreak{}e\allowbreak{}t\allowbreak{}o\allowbreak{}n\allowbreak{}(\allowbreak{})} can host consumer-provided page content while keeping the stock header, footer, command palette, drawer, and quit-confirm shell behavior.

\section{Description}\label{record-130-description}

The \texttt{c\allowbreak{}r\allowbreak{}e\allowbreak{}a\allowbreak{}t\allowbreak{}e\allowbreak{}T\allowbreak{}u\allowbreak{}i\allowbreak{}A\allowbreak{}p\allowbreak{}p\allowbreak{}S\allowbreak{}k\allowbreak{}e\allowbreak{}l\allowbreak{}e\allowbreak{}t\allowbreak{}o\allowbreak{}n} function in \texttt{@\allowbreak{}f\allowbreak{}l\allowbreak{}y\allowbreak{}i\allowbreak{}n\allowbreak{}g\allowbreak{}r\allowbreak{}o\allowbreak{}b\allowbreak{}o\allowbreak{}t\allowbreak{}s\allowbreak{}/\allowbreak{}b\allowbreak{}i\allowbreak{}j\allowbreak{}o\allowbreak{}u\allowbreak{}-\allowbreak{}t\allowbreak{}u\allowbreak{}i\allowbreak{}-\allowbreak{}a\allowbreak{}p\allowbreak{}p} is named and documented as a ``batteries-included design-system shell starter''. However, its internal implementation behaves more like a hardcoded test harness for the framework's own internal documentation (e.g., the \texttt{D\allowbreak{}O\allowbreak{}G\allowbreak{}F\allowbreak{}O\allowbreak{}O\allowbreak{}D} app).

The \texttt{S\allowbreak{}k\allowbreak{}e\allowbreak{}l\allowbreak{}e\allowbreak{}t\allowbreak{}o\allowbreak{}n\allowbreak{}T\allowbreak{}a\allowbreak{}b} interface only accepts an \texttt{i\allowbreak{}d} and a \texttt{t\allowbreak{}i\allowbreak{}t\allowbreak{}l\allowbreak{}e}:

\begin{CodeBlock}
export interface SkeletonTab {
  readonly id: string;
  readonly title: string;
}
\end{CodeBlock}

Because it does not accept a \texttt{r\allowbreak{}e\allowbreak{}n\allowbreak{}d\allowbreak{}e\allowbreak{}r} function or a generic \texttt{F\allowbreak{}r\allowbreak{}a\allowbreak{}m\allowbreak{}e\allowbreak{}P\allowbreak{}a\allowbreak{}g\allowbreak{}e} spec, the skeleton completely ignores any custom UI blocks a consumer tries to render within the tabs. The internal engine statically maps the tabs to pre-defined layout configurations (like the ``Split'' or ``Drawer'' pages) and throws away any external layout logic, resulting in empty or generic screens for consumers who try to use it as a real application starter.

\section{Impact}\label{record-130-impact}

\begin{itemize}
\tightlist
\item
  \textbf{Developer Experience (DX):} New users attempting to use \texttt{@\allowbreak{}f\allowbreak{}l\allowbreak{}y\allowbreak{}i\allowbreak{}n\allowbreak{}g\allowbreak{}r\allowbreak{}o\allowbreak{}b\allowbreak{}o\allowbreak{}t\allowbreak{}s\allowbreak{}/\allowbreak{}b\allowbreak{}i\allowbreak{}j\allowbreak{}o\allowbreak{}u\allowbreak{}-\allowbreak{}t\allowbreak{}u\allowbreak{}i\allowbreak{}-\allowbreak{}a\allowbreak{}p\allowbreak{}p} to scaffold their own applications will encounter ``empty apps'' and assume their layout code is broken.
\item
  \textbf{Architectural Confusion:} It forces consumers to abandon the package entirely and drop down to the lower-level \texttt{c\allowbreak{}r\allowbreak{}e\allowbreak{}a\allowbreak{}t\allowbreak{}e\allowbreak{}F\allowbreak{}r\allowbreak{}a\allowbreak{}m\allowbreak{}e\allowbreak{}d\allowbreak{}A\allowbreak{}p\allowbreak{}p} in \texttt{@\allowbreak{}f\allowbreak{}l\allowbreak{}y\allowbreak{}i\allowbreak{}n\allowbreak{}g\allowbreak{}r\allowbreak{}o\allowbreak{}b\allowbreak{}o\allowbreak{}t\allowbreak{}s\allowbreak{}/\allowbreak{}b\allowbreak{}i\allowbreak{}j\allowbreak{}o\allowbreak{}u\allowbreak{}-\allowbreak{}t\allowbreak{}u\allowbreak{}i} to regain control over their own rendering pipeline.
\end{itemize}

\section{Recommended Fix}\label{record-130-recommended-fix}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Option A (Rename/Deprecate):} Rename the function to \texttt{c\allowbreak{}r\allowbreak{}e\allowbreak{}a\allowbreak{}t\allowbreak{}e\allowbreak{}T\allowbreak{}e\allowbreak{}s\allowbreak{}t\allowbreak{}H\allowbreak{}a\allowbreak{}r\allowbreak{}n\allowbreak{}e\allowbreak{}s\allowbreak{}s\allowbreak{}S\allowbreak{}k\allowbreak{}e\allowbreak{}l\allowbreak{}e\allowbreak{}t\allowbreak{}o\allowbreak{}n} or clearly document that it is strictly for internal framework testing/dogfooding, not for general consumer use.
\item
  \textbf{Option B (Make it Generic):} Update the \texttt{S\allowbreak{}k\allowbreak{}e\allowbreak{}l\allowbreak{}e\allowbreak{}t\allowbreak{}o\allowbreak{}n\allowbreak{}T\allowbreak{}a\allowbreak{}b} interface to accept a \texttt{r\allowbreak{}e\allowbreak{}n\allowbreak{}d\allowbreak{}e\allowbreak{}r} function or \texttt{l\allowbreak{}a\allowbreak{}y\allowbreak{}o\allowbreak{}u\allowbreak{}t} node generator, allowing consumers to inject their own Bijou components (\texttt{S\allowbreak{}u\allowbreak{}r\allowbreak{}f\allowbreak{}a\allowbreak{}c\allowbreak{}e} or \texttt{L\allowbreak{}a\allowbreak{}y\allowbreak{}o\allowbreak{}u\allowbreak{}t\allowbreak{}N\allowbreak{}o\allowbreak{}d\allowbreak{}e}) into the shell's body region while still benefiting from the skeleton's built-in header, footer, and modal orchestration.
\end{enumerate}

\section{Decision}\label{record-130-decision}

Choose Option B.

\texttt{S\allowbreak{}k\allowbreak{}e\allowbreak{}l\allowbreak{}e\allowbreak{}t\allowbreak{}o\allowbreak{}n\allowbreak{}T\allowbreak{}a\allowbreak{}b} should accept:

\begin{itemize}
\tightlist
\item
  \texttt{r\allowbreak{}e\allowbreak{}n\allowbreak{}d\allowbreak{}e\allowbreak{}r\allowbreak{}(\allowbreak{}w\allowbreak{}i\allowbreak{}d\allowbreak{}t\allowbreak{}h\allowbreak{},\allowbreak{} \allowbreak{}h\allowbreak{}e\allowbreak{}i\allowbreak{}g\allowbreak{}h\allowbreak{}t\allowbreak{},\allowbreak{} \allowbreak{}c\allowbreak{}o\allowbreak{}n\allowbreak{}t\allowbreak{}e\allowbreak{}x\allowbreak{}t\allowbreak{})} for single-pane content
\item
  \texttt{l\allowbreak{}a\allowbreak{}y\allowbreak{}o\allowbreak{}u\allowbreak{}t\allowbreak{}(\allowbreak{}c\allowbreak{}o\allowbreak{}n\allowbreak{}t\allowbreak{}e\allowbreak{}x\allowbreak{}t\allowbreak{})} for full frame layout topology
\end{itemize}

Tabs without either option keep the existing default showcase behavior. Tabs with consumer content are treated as custom pages and do not inherit the demo drawer or split layout by index.

\section{Playback questions}\label{record-130-playback-questions}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Can a custom tab render a consumer \texttt{S\allowbreak{}u\allowbreak{}r\allowbreak{}f\allowbreak{}a\allowbreak{}c\allowbreak{}e} inside the stock shell body?
\item
  Can a custom tab provide a full \texttt{F\allowbreak{}r\allowbreak{}a\allowbreak{}m\allowbreak{}e\allowbreak{}L\allowbreak{}a\allowbreak{}y\allowbreak{}o\allowbreak{}u\allowbreak{}t\allowbreak{}N\allowbreak{}o\allowbreak{}d\allowbreak{}e} for splits or grids?
\item
  Does the default two-tab demo still render drawer and split pages?
\item
  Does the skeleton reject ambiguous tabs that define both \texttt{r\allowbreak{}e\allowbreak{}n\allowbreak{}d\allowbreak{}e\allowbreak{}r} and \texttt{l\allowbreak{}a\allowbreak{}y\allowbreak{}o\allowbreak{}u\allowbreak{}t}?
\end{enumerate}

\section{Accessibility / assistive reading posture}\label{record-130-accessibility-assistive-reading-posture}

No new accessibility surface is added in this slice. The important behavior is that consumer content enters the existing frame/layout/focus machinery instead of being bypassed or replaced by demo pages.

\section{Localization / directionality posture}\label{record-130-localization-directionality-posture}

No new localization behavior. Consumer content remains owned by the consumer renderer or layout factory.

\section{Agent inspectability / explainability posture}\label{record-130-agent-inspectability-explainability-posture}

The public \texttt{S\allowbreak{}k\allowbreak{}e\allowbreak{}l\allowbreak{}e\allowbreak{}t\allowbreak{}o\allowbreak{}n\allowbreak{}T\allowbreak{}a\allowbreak{}b} contract makes page ownership inspectable from the app declaration. The skeleton shell no longer hides consumer intent behind index-based demo page selection.

\section{Implementation outline}\label{record-130-implementation-outline}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Extend \texttt{S\allowbreak{}k\allowbreak{}e\allowbreak{}l\allowbreak{}e\allowbreak{}t\allowbreak{}o\allowbreak{}n\allowbreak{}T\allowbreak{}a\allowbreak{}b} with optional \texttt{r\allowbreak{}e\allowbreak{}n\allowbreak{}d\allowbreak{}e\allowbreak{}r} and \texttt{l\allowbreak{}a\allowbreak{}y\allowbreak{}o\allowbreak{}u\allowbreak{}t} hooks.
\item
  Reject tabs that define both hooks.
\item
  Treat hook-backed tabs as custom pages instead of default demo pages.
\item
  Add focused tests for custom render, custom layout, default behavior, and ambiguous tab rejection.
\end{enumerate}
