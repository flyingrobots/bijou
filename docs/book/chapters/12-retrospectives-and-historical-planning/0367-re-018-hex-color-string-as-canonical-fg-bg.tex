\section{Problem}\label{record-367-problem}

Throughout the bijou API surface, foreground and background colors are represented as \texttt{'\allowbreak{}\#\allowbreak{}r\allowbreak{}r\allowbreak{}g\allowbreak{}g\allowbreak{}b\allowbreak{}b\allowbreak{}'} strings on the \texttt{C\allowbreak{}e\allowbreak{}l\allowbreak{}l} interface:

\begin{CodeBlock}
interface Cell {
  fg?: string;  // '#rrggbb'
  bg?: string;  // '#rrggbb'
  ...
}
\end{CodeBlock}

Every single \texttt{s\allowbreak{}u\allowbreak{}r\allowbreak{}f\allowbreak{}a\allowbreak{}c\allowbreak{}e\allowbreak{}.\allowbreak{}s\allowbreak{}e\allowbreak{}t\allowbreak{}(\allowbreak{}x\allowbreak{},\allowbreak{} \allowbreak{}y\allowbreak{},\allowbreak{} \allowbreak{}\{\allowbreak{} \allowbreak{}f\allowbreak{}g\allowbreak{},\allowbreak{} \allowbreak{}b\allowbreak{}g\allowbreak{},\allowbreak{} \allowbreak{}.\allowbreak{}.\allowbreak{}.\allowbreak{} \allowbreak{}\}\allowbreak{})} call has to parse these strings into bytes before writing to the packed buffer. The parse happens via \texttt{i\allowbreak{}n\allowbreak{}l\allowbreak{}i\allowbreak{}n\allowbreak{}e\allowbreak{}H\allowbreak{}e\allowbreak{}x\allowbreak{}R\allowbreak{}G\allowbreak{}B} in \texttt{p\allowbreak{}a\allowbreak{}c\allowbreak{}k\allowbreak{}a\allowbreak{}g\allowbreak{}e\allowbreak{}s\allowbreak{}/\allowbreak{}b\allowbreak{}i\allowbreak{}j\allowbreak{}o\allowbreak{}u\allowbreak{}/\allowbreak{}s\allowbreak{}r\allowbreak{}c\allowbreak{}/\allowbreak{}p\allowbreak{}o\allowbreak{}r\allowbreak{}t\allowbreak{}s\allowbreak{}/\allowbreak{}s\allowbreak{}u\allowbreak{}r\allowbreak{}f\allowbreak{}a\allowbreak{}c\allowbreak{}e\allowbreak{}.\allowbreak{}t\allowbreak{}s} (6 \texttt{c\allowbreak{}h\allowbreak{}a\allowbreak{}r\allowbreak{}C\allowbreak{}o\allowbreak{}d\allowbreak{}e\allowbreak{}A\allowbreak{}t}s + 6 \texttt{h\allowbreak{}e\allowbreak{}x\allowbreak{}D} lookups + bit shuffles per color). For a paint-heavy frame that sets every cell of a 220×58 surface with both fg and bg, that's \textbf{25,520 hex parses per frame} --- and the theme vocabulary is \textasciitilde15 unique colors.

24,505 of those parses are wasted work because they recompute the same bytes over and over for the same theme colors.

Paint scenarios that use \texttt{s\allowbreak{}e\allowbreak{}t\allowbreak{}R\allowbreak{}G\allowbreak{}B} (which takes pre-parsed bytes) are less affected in principle, but are still dominated by the paint cost because most components still call \texttt{s\allowbreak{}u\allowbreak{}r\allowbreak{}f\allowbreak{}a\allowbreak{}c\allowbreak{}e\allowbreak{}.\allowbreak{}s\allowbreak{}e\allowbreak{}t\allowbreak{}(\allowbreak{}\{\allowbreak{}f\allowbreak{}g\allowbreak{},\allowbreak{} \allowbreak{}b\allowbreak{}g\allowbreak{}\}\allowbreak{})}.

\section{Why This Is Bad}\label{record-367-why-this-is-bad}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Repeated work.} The same hex string parses to the same bytes every time. There is no state in a hex string; no reason to re-parse it.
\item
  \textbf{API boundary at the wrong layer.} Hex strings are a \emph{user input} format. They belong at the edge of the system where a human types \texttt{\#\allowbreak{}f\allowbreak{}f\allowbreak{}8\allowbreak{}8\allowbreak{}0\allowbreak{}0} into a theme file. They do not belong in the hot path that runs thousands of times per frame.
\item
  \textbf{Encourages callers to bypass the safe API.} Components have already started caching their own parsed bytes to avoid the overhead (\texttt{p\allowbreak{}r\allowbreak{}e\allowbreak{}f\allowbreak{}e\allowbreak{}r\allowbreak{}e\allowbreak{}n\allowbreak{}c\allowbreak{}e\allowbreak{}-\allowbreak{}l\allowbreak{}i\allowbreak{}s\allowbreak{}t\allowbreak{}.\allowbreak{}t\allowbreak{}s} caches \texttt{p\allowbreak{}a\allowbreak{}r\allowbreak{}s\allowbreak{}e\allowbreak{}H\allowbreak{}e\allowbreak{}x} results in locals). This is a smell --- it means the safe API is too slow to use safely, so callers build their own shortcuts.
\end{enumerate}

\section{Fix Direction}\label{record-367-fix-direction}

Two options that compose:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Theme-token color cache.} When a theme is loaded, pre-parse every hex color into a \texttt{U\allowbreak{}i\allowbreak{}n\allowbreak{}t\allowbreak{}8\allowbreak{}A\allowbreak{}r\allowbreak{}r\allowbreak{}a\allowbreak{}y} (3 bytes). Expose a resolved theme that holds bytes, not strings. Components that pull colors from theme tokens get pre-parsed bytes for free. See the related cool idea \texttt{R\allowbreak{}E\allowbreak{}-\allowbreak{}0\allowbreak{}1\allowbreak{}9\allowbreak{}-\allowbreak{}t\allowbreak{}h\allowbreak{}e\allowbreak{}m\allowbreak{}e\allowbreak{}-\allowbreak{}t\allowbreak{}o\allowbreak{}k\allowbreak{}e\allowbreak{}n\allowbreak{}-\allowbreak{}c\allowbreak{}o\allowbreak{}l\allowbreak{}o\allowbreak{}r\allowbreak{}-\allowbreak{}c\allowbreak{}a\allowbreak{}c\allowbreak{}h\allowbreak{}e\allowbreak{}.\allowbreak{}m\allowbreak{}d}.
\item
  \textbf{Typed color representation at the API boundary.} Introduce a branded \texttt{C\allowbreak{}o\allowbreak{}l\allowbreak{}o\allowbreak{}r\allowbreak{}R\allowbreak{}e\allowbreak{}f} type (an opaque wrapper around a packed uint32 or a \texttt{U\allowbreak{}i\allowbreak{}n\allowbreak{}t\allowbreak{}8\allowbreak{}A\allowbreak{}r\allowbreak{}r\allowbreak{}a\allowbreak{}y}) and make \texttt{C\allowbreak{}e\allowbreak{}l\allowbreak{}l\allowbreak{}.\allowbreak{}f\allowbreak{}g}/\texttt{C\allowbreak{}e\allowbreak{}l\allowbreak{}l\allowbreak{}.\allowbreak{}b\allowbreak{}g} accept \texttt{C\allowbreak{}o\allowbreak{}l\allowbreak{}o\allowbreak{}r\allowbreak{}R\allowbreak{}e\allowbreak{}f\allowbreak{} \allowbreak{}|\allowbreak{} \allowbreak{}s\allowbreak{}t\allowbreak{}r\allowbreak{}i\allowbreak{}n\allowbreak{}g}. Hex strings stay supported for human-written code, but library internals and components thread \texttt{C\allowbreak{}o\allowbreak{}l\allowbreak{}o\allowbreak{}r\allowbreak{}R\allowbreak{}e\allowbreak{}f} end to end. Hex parsing happens only at the string → ColorRef boundary, once. See cool idea \texttt{R\allowbreak{}E\allowbreak{}-\allowbreak{}0\allowbreak{}2\allowbreak{}0\allowbreak{}-\allowbreak{}t\allowbreak{}y\allowbreak{}p\allowbreak{}e\allowbreak{}d\allowbreak{}-\allowbreak{}c\allowbreak{}o\allowbreak{}l\allowbreak{}o\allowbreak{}r\allowbreak{}-\allowbreak{}r\allowbreak{}e\allowbreak{}p\allowbreak{}r\allowbreak{}e\allowbreak{}s\allowbreak{}e\allowbreak{}n\allowbreak{}t\allowbreak{}a\allowbreak{}t\allowbreak{}i\allowbreak{}o\allowbreak{}n\allowbreak{}.\allowbreak{}m\allowbreak{}d}.
\end{enumerate}

Both preserve API compatibility for user code while making the hot path allocation-free.

\section{Impact}\label{record-367-impact}

Measuring against the RE-017 post-merge baseline:

\begin{itemize}
\tightlist
\item
  \texttt{p\allowbreak{}a\allowbreak{}i\allowbreak{}n\allowbreak{}t\allowbreak{}-\allowbreak{}s\allowbreak{}e\allowbreak{}t\allowbreak{}-\allowbreak{}h\allowbreak{}e\allowbreak{}x\allowbreak{}-\allowbreak{}p\allowbreak{}a\allowbreak{}l\allowbreak{}e\allowbreak{}t\allowbreak{}t\allowbreak{}e} at 220×58: 634 µs/frame, 12,760 cells, \textasciitilde2 hex parses per cell (fg + bg). Roughly \textasciitilde25,000 parses / frame.
\item
  If each parse is \textasciitilde200 ns (conservative), that's 5 ms of parse work per frame, dwarfing the 634 µs total. But the actual parse cost is much lower (maybe 20-50 ns each), making total parse cost \textasciitilde500 µs-1 ms per frame --- still a significant fraction of frame time on paint-heavy workloads.
\end{itemize}

Confirming the magnitude is a task in RE-017 (I-0e). This entry captures the structural smell regardless of the exact number.
