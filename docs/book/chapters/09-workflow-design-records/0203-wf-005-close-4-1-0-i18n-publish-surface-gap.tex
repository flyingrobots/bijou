\section{Hill}\label{record-203-hill}

The \texttt{4\allowbreak{}.\allowbreak{}1\allowbreak{}.\allowbreak{}0} i18n package story is no longer ambiguous.

The publish workflow, release dry-run workflow, release docs, and workflow signposts all agree that the four i18n packages are part of the automated \texttt{4\allowbreak{}.\allowbreak{}1\allowbreak{}.\allowbreak{}0} release surface.

\section{Why this cycle exists}\label{record-203-why-this-cycle-exists}

\href{https://github.com/flyingrobots/bijou/blob/cbd70612140e7a450d764b3c7be1c6af878b99bc/docs/design/WF-004-shape-the-next-release.md}{WF-004} made \texttt{4\allowbreak{}.\allowbreak{}1\allowbreak{}.\allowbreak{}0} an explicit, inspectable release decision, but it also surfaced a real contradiction:

\begin{itemize}
\tightlist
\item
  the workspace and long-form release docs already treated the i18n packages as part of the \texttt{4\allowbreak{}.\allowbreak{}1\allowbreak{}.\allowbreak{}0} story
\item
  the automated publish workflows still only packed and published the older five-package surface
\end{itemize}

That meant the repo could not honestly answer a simple question:

Are the i18n packages part of the public \texttt{4\allowbreak{}.\allowbreak{}1\allowbreak{}.\allowbreak{}0} release or not?

This cycle exists to close that gap in code, docs, and tests.

\section{Decision}\label{record-203-decision}

The four i18n packages are part of the planned public \texttt{4\allowbreak{}.\allowbreak{}1\allowbreak{}.\allowbreak{}0} release.

Bijou should therefore:

\begin{itemize}
\tightlist
\item
  pack them in the tag publish verification workflow
\item
  dry-run publish them in the release dry-run workflow
\item
  publish them from the real tag-driven npm workflow
\item
  describe them as real \texttt{4\allowbreak{}.\allowbreak{}1\allowbreak{}.\allowbreak{}0} release artifacts in repo docs
\end{itemize}
