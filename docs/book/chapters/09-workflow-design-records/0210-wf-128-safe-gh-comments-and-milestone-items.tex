\section{Framing}\label{record-210-framing}

Two small workflow defects came out of the V7 closeout:

\begin{itemize}
\tightlist
\item
  review comments can be corrupted when Markdown literals are passed through a shell-interpolated \texttt{g\allowbreak{}h\allowbreak{} \allowbreak{}p\allowbreak{}r\allowbreak{} \allowbreak{}c\allowbreak{}o\allowbreak{}m\allowbreak{}m\allowbreak{}e\allowbreak{}n\allowbreak{}t\allowbreak{} \allowbreak{}-\allowbreak{}-\allowbreak{}b\allowbreak{}o\allowbreak{}d\allowbreak{}y\allowbreak{} \allowbreak{}"\allowbreak{}.\allowbreak{}.\allowbreak{}.\allowbreak{}"} argument
\item
  roadmap release snapshots can be misread when GitHub milestone totals include pull requests as milestone items while nearby prose says ``issues''
\end{itemize}

Both are process bugs. They do not change runtime behavior, but they do affect the reliability of review evidence and release bookkeeping.

\section{Sponsored Users}\label{record-210-sponsored-users}

\begin{itemize}
\tightlist
\item
  A maintainer posting self-review, Code Lawyer, or activity-summary comments needs a command pattern that preserves Markdown literally.
\item
  A release maintainer reading \texttt{R\allowbreak{}O\allowbreak{}A\allowbreak{}D\allowbreak{}M\allowbreak{}A\allowbreak{}P\allowbreak{}.\allowbreak{}m\allowbreak{}d} needs to know whether the snapshot counts GitHub milestone items or issue-only rows.
\item
  A review agent needs executable repo tests that catch unsafe comment examples and ambiguous milestone-count language before the pattern spreads.
\end{itemize}

\section{Hill}\label{record-210-hill}

A maintainer can post Markdown-heavy GitHub comments and reconcile release snapshot rows without relying on memory: \texttt{d\allowbreak{}o\allowbreak{}c\allowbreak{}s\allowbreak{}/\allowbreak{}W\allowbreak{}O\allowbreak{}R\allowbreak{}K\allowbreak{}F\allowbreak{}L\allowbreak{}O\allowbreak{}W\allowbreak{}.\allowbreak{}m\allowbreak{}d}, \texttt{d\allowbreak{}o\allowbreak{}c\allowbreak{}s\allowbreak{}/\allowbreak{}M\allowbreak{}E\allowbreak{}T\allowbreak{}H\allowbreak{}O\allowbreak{}D\allowbreak{}.\allowbreak{}m\allowbreak{}d}, and \texttt{d\allowbreak{}o\allowbreak{}c\allowbreak{}s\allowbreak{}/\allowbreak{}R\allowbreak{}O\allowbreak{}A\allowbreak{}D\allowbreak{}M\allowbreak{}A\allowbreak{}P\allowbreak{}.\allowbreak{}m\allowbreak{}d} state the safe conventions, and WF-128 tests prove those conventions stay visible.

\section{Current Truth}\label{record-210-current-truth}

\begin{itemize}
\tightlist
\item
  Issue \#287 records that a PR \#284 self-review comment was polluted when Markdown backticks inside a double-quoted \texttt{-\allowbreak{}-\allowbreak{}b\allowbreak{}o\allowbreak{}d\allowbreak{}y} argument were evaluated by the shell.
\item
  Issue \#288 records that V7 tracker-sync work had to count milestone PRs \#278 and \#280 to match GitHub milestone totals.
\item
  \texttt{d\allowbreak{}o\allowbreak{}c\allowbreak{}s\allowbreak{}/\allowbreak{}W\allowbreak{}O\allowbreak{}R\allowbreak{}K\allowbreak{}F\allowbreak{}L\allowbreak{}O\allowbreak{}W\allowbreak{}.\allowbreak{}m\allowbreak{}d} and \texttt{d\allowbreak{}o\allowbreak{}c\allowbreak{}s\allowbreak{}/\allowbreak{}M\allowbreak{}E\allowbreak{}T\allowbreak{}H\allowbreak{}O\allowbreak{}D\allowbreak{}.\allowbreak{}m\allowbreak{}d} do not currently name the \texttt{-\allowbreak{}-\allowbreak{}b\allowbreak{}o\allowbreak{}d\allowbreak{}y\allowbreak{}-\allowbreak{}f\allowbreak{}i\allowbreak{}l\allowbreak{}e} / literal-heredoc path for review comments.
\item
  \texttt{d\allowbreak{}o\allowbreak{}c\allowbreak{}s\allowbreak{}/\allowbreak{}R\allowbreak{}O\allowbreak{}A\allowbreak{}D\allowbreak{}M\allowbreak{}A\allowbreak{}P\allowbreak{}.\allowbreak{}m\allowbreak{}d} says GitHub milestones and issue labels are live tracker state, but the release snapshot columns are named only \texttt{O\allowbreak{}p\allowbreak{}e\allowbreak{}n} and \texttt{C\allowbreak{}l\allowbreak{}o\allowbreak{}s\allowbreak{}e\allowbreak{}d}, which makes item counts look like issue-only counts.
\end{itemize}

\section{Product Shape}\label{record-210-product-shape}

\subsection{Safe Comment Posting}\label{record-210-safe-comment-posting}

\begin{CodeBlock}
Workflow review step
  self-review / Code Lawyer / activity summary
    |
    v
  gh pr comment "$PR_NUMBER" --body-file - <<'EOF'
  Markdown stays literal:
  - `commands`
  - $()
  - tables
  EOF
\end{CodeBlock}

The rule is intentionally boring: if a GitHub comment body contains Markdown, commands, backticks, \texttt{\$\allowbreak{}(\allowbreak{})}, tables, or copied review output, post it through \texttt{-\allowbreak{}-\allowbreak{}b\allowbreak{}o\allowbreak{}d\allowbreak{}y\allowbreak{}-\allowbreak{}f\allowbreak{}i\allowbreak{}l\allowbreak{}e} with a quoted heredoc or a real file.

\subsection{Milestone Item Mirrors}\label{record-210-milestone-item-mirrors}

\begin{CodeBlock}
GitHub milestone page / API
  open milestone items   = issues + pull requests assigned to milestone
  closed milestone items = issues + pull requests assigned to milestone

ROADMAP release snapshot
  Open Items / Closed Items
  Completed lineage includes milestone PR rows when PRs contribute to totals.
\end{CodeBlock}
